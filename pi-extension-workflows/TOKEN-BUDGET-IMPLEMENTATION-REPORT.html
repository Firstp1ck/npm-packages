Root cause, enforcement design, and implementation

Earlier WebUI planning workflows failed with run and phase token-budget errors before returning completed scout output. The runtime checked aggregate budgets before dispatch and after a task returned, but it had no active reservation, no per-call enforcement, and no cumulative failed-attempt accounting. Parallel calls could therefore pass the same admission check, while one subprocess could continue consuming tokens until the aggregate envelope was already exhausted.

Design boundary: Pi reports authoritative usage at assistant message_end. The parent can stop future turns and terminate the process group, but cannot interrupt an already streaming response at an exact token. One-response overshoot is therefore documented and bounded rather than hidden.

Implemented contract and runtime behavior

Contract

Policy and call controls

meta.pi.budgets.agent.maxTokens and maxTurns are optional positive integers. Per-call values may tighten but never loosen the policy or derived allowance, and they participate in replay fingerprints.

Admission

Deterministic quantum

Each token scope derives max(1, floor(maxTokens / max(2, maxConcurrency))). The reservation is the minimum positive run, phase, policy, and request allowance after measured usage and active reservations.

Finalization

Useful answer before exhaustion

A token-bounded call without an explicit turn cap receives eight turns. The prompt asks the agent to use tools selectively and return its concise best answer before the final allowed turn. A natural stop exactly at the boundary succeeds.

Evidence

Failures retain value

Budget termination is structured as budget_exhausted, never retried, and evaluated before structured-output validation. Partial text, raw events, cumulative usage, and failed-call result evidence survive.

Retries

Every attempt charged

Reservations are acquired per attempt and reconciled once. Failed-attempt usage is merged with later success, while contextTokens keeps its maximum rather than being summed.

Replay

No duplicate work

Replay resolves before admission, reserves nothing, starts no subprocess, and charges cached usage exactly once. A replay hit can legitimately exhaust the current logical budget.

Key changed surfaces

Core runtime changes are concentrated in src/token-budget.ts, src/script-runner.ts, and src/task-runner.ts. Contract/type changes span src/types.ts, src/script-schema.ts, src/script-runtime.ts, src/call-fingerprint.ts, and workflow-runtime.d.ts. Existing schema-v1 evidence is exposed through src/run-manager.ts. Documentation and deterministic fixtures/tests were added or expanded under README.md and tests/.

Release posture, limitations, and next actions

  1. Inspect and commit intentionally. The package changes, plan, tests, and this report remain unstaged and uncommitted. Sibling pi-package-webui changes are out of scope and must not be bundled accidentally.
  2. Optionally run a live bounded read-only smoke. This is useful evidence when a subscription provider is available, but it is not the deterministic release gate.
  3. Preserve the documented enforcement boundary. Usage is authoritative only at message_end; do not promise exact mid-response interruption.
  4. Keep rollback coupled. If enforcement is removed before release, token-budgeted calls should fail closed rather than silently returning to retrospective-only aggregate checks.
